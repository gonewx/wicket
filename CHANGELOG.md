## [0.6.1] - 2026-11-15

### Added

- `storagetest`: a MAY case for `RefreshTokenStore`, `LifetimeUpdateRoundTrips` (`CreationTime` and `Lifetime` survive an update, and `RemoveExpired` judges the record by the updated values). No MUST case changed; `SuiteVersion` stays `2.0.0`. A host-provided `RefreshTokenStore` has to write `CreationTime` and `Lifetime` back on every update, since the core dates records stored without a creation time and sliding expiration rewrites the lifetime on each redemption.

### Security

- Refresh token redemption is bound to the client the token was issued to: a refresh token presented by any other client is refused with `invalid_grant`, as if it did not exist, and the owning client can still redeem it. Releases 0.1.0 through 0.6.0 did not compare the refresh token's client with the authenticated client, so any authenticated client holding another client's refresh token could redeem it and receive tokens issued to that client. Neither wicket's logs nor its stores identify such a redemption: the success record carries no client id and the tokens issued belong to the owning client. Hosts that issue refresh tokens to more than one client and cannot rule out that a refresh token reached another client should revoke the outstanding refresh tokens of the affected clients (`RefreshTokenStore.RemoveRefreshTokensByClient`); access tokens already issued from them stay valid until they expire.

### Fixed

- Refresh token lifetimes are recorded and enforced. `RefreshTokenService.CreateRefreshToken` never set `CreationTime` or `Lifetime`, and redemption never checked expiry, so in 0.5.0 and 0.6.0 refresh tokens did not expire, while a host calling `RefreshTokenStore.RemoveExpired(now)` as documented removed every refresh token, valid ones included. A refresh token now records its creation time and the lifetime its client grants, and an expired one is refused with `invalid_grant`, as if it did not exist; the record stays until the host reclaims it. Absolute expiration (the `models.NewClient()` default) ends at creation plus `AbsoluteRefreshTokenLifetime`; sliding expiration with a positive `SlidingRefreshTokenLifetime` moves the expiry to the redemption time plus that lifetime on every redemption, capped at creation plus `AbsoluteRefreshTokenLifetime` unless that is 0. A lifetime setting of 0 sets no limit; when nothing limits a token, `Lifetime` is `math.MaxInt32` seconds so that `RemoveExpired` keeps it. `(*services/impl.RefreshTokenService).SetClock(clock)` sets the clock the service dates lifetimes with (nil panics); without one the wall clock is used. It is a method of the concrete service, for services built outside the container; no interface changed.
  - Upgrade note: the 30-day default absolute lifetime of `models.NewClient()` now takes effect. Clients that relied on refresh tokens never expiring must set `AbsoluteRefreshTokenLifetime` (and, for sliding expiration, `SlidingRefreshTokenLifetime`) to 0 or to the lifetime they want.
  - Upgrade note: refresh token records issued before 0.6.1 have a zero `CreationTime`. Their first successful redemption after the upgrade dates them (`CreationTime` is set to that moment and `Lifetime` follows the client's current settings) and writes them back; a redemption refused while the request is validated (scope, resource or DPoP binding, for instance) writes nothing, and the record keeps its zero `CreationTime`, but `RemoveExpired` removes every record still carrying a zero `CreationTime`. Hosts that want to keep outstanding refresh tokens backfill `CreationTime` and `Lifetime` before the first `RemoveExpired` after the upgrade; adapters that derive an expiry column from `CreationTime + Lifetime` update that column with the backfill and recompute it on every `UpdateRefreshToken`, since sliding expiration rewrites `Lifetime` on each redemption. See "既有 refresh token 记录的迁移" in `docs/storage-persistence-guide.md`.

## [0.6.0] - 2026-11-15

### Added

- DPoP (RFC 9449) at the token endpoint, off by default. `ServerConfig.EnableDPoP(dpop.Options)` is the only switch (it panics after `Freeze()`; query `DPoPEnabled()`, `DPoPOptions()`); `EndpointsOptions` has no switch for it. `dpop.Options` holds `SigningAlgorithms` (a subset of `clientassertion.SupportedSigningAlgorithms()`, the default), `ProofLifetime` (60s, at most 10 minutes) and `ClockSkew` (60s, at most 10 minutes); `Freeze()` panics on options that do not validate. Once enabled, the replay registry seam becomes required, as for `private_key_jwt`. While DPoP is not enabled the token endpoint does not read the `DPoP` header and every response is unchanged.
- Once enabled, a token request may carry one `DPoP` header holding a proof. Before client authentication the proof is checked statelessly: one compact JWS, `typ` `dpop+jwt`, a configured `alg`, a public `jwk` matching `alg` and no `crit`, a signature verified with that `jwk`, and the claims `jti` (at most 256 bytes), `htm`, `htu` (the base URL of the request plus its path, scheme and host case-insensitive, default port, query and fragment ignored) and `iat` (within `ProofLifetime` and `ClockSkew`). After client authentication the proof `jti` is registered with the replay registry under `replay.Key(replay.PurposeDPoPProof(), <JWK thumbprint>, jti)` until max(`iat` + `ProofLifetime`, now) + `ClockSkew` (with server nonces required, the nonce deadline also takes part, see below). An invalid or replayed proof answers 400 `invalid_dpop_proof` (`wicket.TokenErrorsInvalidDPoPProof`); a refused proof consumes no authorization code. A registry failure other than a duplicate answers the fixed 500 used for unavailable client authentication. The token endpoint does not judge `ath`; resource-side checks judge it through `(*dpop.Verifier).VerifyForResource` (userinfo and the JWT bearer handler, see below). `nonce` is judged only while server nonces are required (see below).
- An access token issued with an accepted proof carries `cnf` `{"jkt":"<RFC 7638 SHA-256 thumbprint>"}` (in the JWT, or in the `cnf` claim of a reference token's stored copy) and the response `token_type` is `DPoP` (`wicket.TokenResponseTypesDPoP`). With mutual TLS certificate binding also enabled, the confirmation holds both `x5t#S256` and `jkt`; `services.CombineAccessTokenConfirmations` merges the two binders.
- `RefreshToken.DPoPKeyThumbprint` (embedded `models.RefreshTokenProofBinding`): the refresh token of a public client issued with a proof is bound to the proof key when it is created. Redeeming it without a proof, or with a proof made with another key, answers `invalid_grant` before the refresh token is written. Refresh tokens of confidential clients are not bound. Persistence adapters must round-trip the field; the storage conformance suite does not check it.
- `Client.RequireDPoP` (embedded `models.ClientDPoPMetadata`, corresponding to `dpop_bound_access_tokens`): a token request of such a client without a proof answers `invalid_request` with the description `DPoP proof required`. A client requiring DPoP while DPoP is not enabled, or while it allows access tokens via the browser, is an invalid configuration (`storage.ErrInvalidClientConfiguration`) and is refused rather than served bearer tokens.
- Discovery advertises `dpop_signing_alg_values_supported` with the configured algorithms while DPoP is enabled, and never otherwise; a custom entry under that name is dropped with a warning.
- `TokenResponse.TokenType` (embedded `responses/models.TokenResponseTokenType`): the `token_type` of a token response; empty stands for `Bearer`.
- `dpop_jkt` (RFC 9449 §10, `wicket.AuthorizeRequestDPoPJkt`): while DPoP is enabled, an authorize request, direct or pushed through PAR, may name the thumbprint of a DPoP key (43 characters of canonical unpadded base64url, 32 bytes); a malformed value answers `invalid_request` (`Invalid dpop_jkt`), also at the PAR endpoint. The thumbprint is stored with the code as `AuthorizationCode.DPoPKeyThumbprint` (embedded `models.AuthorizationCodeProofBinding`); redeeming the code without a proof, or with a proof made with another key, answers `invalid_grant` after the code was taken, so the code is spent. While DPoP is not enabled the parameter is ignored. The PAR endpoint does not read the `DPoP` header. Persistence adapters must round-trip the field; the storage conformance suite does not check it.
- DPoP server nonces (RFC 9449 §8), off by default: `dpop.Options.RequireNonce` and `NonceLifetime` (5 minutes, at most 10). Once on, every response to a token request carrying a `DPoP` header carries a fresh nonce in `DPoP-Nonce` (`wicket.DPoPNonceHeaderName`), and a proof without an accepted `nonce` claim answers 400 `use_dpop_nonce` (`wicket.TokenErrorsUseDPoPNonce`) before client authentication and before any registration, so neither the code nor an assertion `jti` is consumed. Nonces are stateless HMAC-SHA256 values bound to `authorization-server <issuer>`, stored nowhere; the proof `jti` registration then lasts until the later of `iat` + `ProofLifetime`, the nonce deadline and now, plus `ClockSkew`. A key source failure answers the fixed 500. `dpop.NonceKey`, `dpop.NonceKeySource`, `dpop.NewStaticNonceKeys`, `dpop.ValidateNonceKeys`, `dpop.NonceSealer` (`NewNonceSealer`, `Issue`, `Check`) and `dpop.ErrInvalidNonce` are exported for reuse; `dpop.Proof` gains `Nonce` and `NonceDeadline`.
- `ServerConfig.SetDPoPNonceKeys(dpop.NonceKeySource)`: the DPoP nonce key seam, feature-required while DPoP is enabled with `RequireNonce`. It has no fallback: `AllowInMemoryFallback()` does not cover it, and `Freeze()` panics when it is missing or its keys are unreadable or invalid (secret under 32 bytes, id empty, over 32 bytes, outside `[A-Za-z0-9._-]` or repeated). It is unrelated to `dp.DataProtectionProvider` and never read while nonces are not required. Rotation: deploy the new key as previous on every replica, switch it to current, keep the old key as previous for at least `NonceLifetime` + `ClockSkew`.
- DPoP at the userinfo endpoint (RFC 9449 §7), wired by `(*handlers.UserInfoHandler).SetDPoP(verifier, registry, options, clock)`, which the container calls only while DPoP is enabled: userinfo then accepts `Authorization: DPoP <access token>` (scheme matched without regard to case, `wicket.AuthenticationSchemesAuthorizationHeaderDPoP`) with a proof for the request whose `ath` is the token hash and whose key thumbprint equals the token's `cnf.jkt`. The proof `jti` is registered only after every other check passed. A bad, missing or replayed proof or `ath` answers 401 `invalid_dpop_proof`; an invalid, expired or unbound token, another key or a malformed `cnf` answers 401 `invalid_token`; a malformed `DPoP` header or a form `access_token` alongside it answers 400 `invalid_request`; a registry failure answers the fixed 500. Every such rejection carries one `WWW-Authenticate: DPoP error="…"[, error_description="…"], algs="…"` value and `Cache-Control: no-store`. Server nonces do not apply to userinfo. The certificate binding check still applies to tokens bound both ways.
- `dpop.AccessTokenHash`, `(*dpop.Verifier).VerifyForResource` (every `Verify` check plus `ath`), `dpop.ConfirmationThumbprint` (reads `cnf` as an object or its JSON text, `dpop.ErrMalformedConfirmation`) and `dpop.ThumbprintMatches`, for resource side DPoP checks. `Verify` is unchanged and still ignores `ath`.
- `results.NewDPoPChallengeResult` writes a DPoP authentication challenge.
- Introspection returns the `cnf` of DPoP bound JWT and reference access tokens, now covered by tests.
- DPoP validation in the JWT bearer handler (`auth/jwt`, RFC 9449 §7), off by default: `jwt.Options.DPoP *jwt.DPoPValidation`, nil disables it and leaves the handler unchanged (the `DPoP` scheme is not read and the challenge stays the bare 401). The only way to build a usable value is `jwt.NewDPoPValidation(jwt.DPoPValidationConfig)`; there is no `ServerConfig` switch and no container registration, since a resource server is usually not the authorization server process. `DPoPValidationConfig` holds `Options` (`dpop.Options`; `RequireNonce` selects the server nonce freshness mode), `Registry` (`replay.Registry`, required, no in-memory fallback: pass `replay.NewMemoryRegistry()` explicitly; the host reclaims records with `RemoveExpired`), `NonceKeys` and `Resource` (both required in the nonce mode, ignored otherwise) and an optional `RequestUri func(*http.Request) string` overriding the `htu` the proof has to name (by default `scheme://Host/path`, `https` when the request arrived over TLS). Invalid options, a missing registry, or in the nonce mode a missing, failing or invalid nonce key source or an empty resource make `NewDPoPValidation` fail with an error matching `jwt.ErrInvalidDPoPConfiguration`, before the first request. A `DPoPValidation` not made by the constructor fails every request with a 500.
- Once set, the handler accepts `Authorization: DPoP <access token>` (scheme matched without regard to case) with a proof whose signature, `typ`, `alg`, `htm`, `htu`, `iat` and `ath` pass `VerifyForResource`; in the nonce mode the proof also has to carry an unexpired nonce issued for `resource-server <Resource>` (a nonce of the authorization server is refused, and the other way round). The token is then validated as before, the certificate binding check still applies, the proof key thumbprint has to equal the token's `cnf.jkt`, and only then is the proof `jti` registered, at most once per authentication, until the later of `iat` + `ProofLifetime`, the nonce deadline (nonce mode) and now, plus `ClockSkew`. A bound token or a malformed `cnf` presented as a bearer token fails; an unbound bearer token passes as before, its `DPoP` header ignored. While set, a token produced by a custom `SecurityTokenValidator` fails.
- Failures use fixed sentinels that never wrap the underlying error text: `jwt.ErrDPoPProofRejected` (missing, invalid or replayed proof, `ath` mismatch), `jwt.ErrDPoPNonceRequired`, `jwt.ErrDPoPTokenBinding`, `jwt.ErrDPoPMalformedAuthorization` and `jwt.ErrDPoPUnavailable` (registry or nonce key source failure, logged with the error type only).
- `(*jwt.Handler).HandleChallenge`: while `Options.DPoP` is set, the challenge follows the authentication result of the request, with one `WWW-Authenticate` value, `Cache-Control: no-store` and no body: no token 401 `DPoP algs="…"`; `ErrDPoPProofRejected` 401 `invalid_dpop_proof`; `ErrDPoPNonceRequired` 401 `use_dpop_nonce` with the description `DPoP proof must carry the server nonce`; `ErrDPoPMalformedAuthorization` 400 `invalid_request`; `ErrDPoPUnavailable` a bare 500; any other failure 401 `invalid_token`. In the nonce mode every 401 carries a fresh nonce in `DPoP-Nonce`, and a nonce that cannot be issued turns the answer into the bare 500. The `OnChallenge` event is not raised while DPoP validation is on. Successful responses carry no nonce.
- `results.DPoPChallengeResult.Nonce`, sent in `DPoP-Nonce` when not empty, and `results.NewDPoPAlgorithmsChallengeResult`, the challenge without an `error` parameter.

### Changed

- userinfo refuses a token bound to a DPoP key (`cnf.jkt`), or one with a malformed `cnf`, presented as a bearer token (header or form) once the token otherwise validates, with 401 `invalid_token`: a DPoP challenge while DPoP is enabled, the existing bearer challenge otherwise. Validator errors (invalid, expired, insufficient scope) are answered as before. Such tokens were accepted as bearer tokens while DPoP was disabled; they can only have been issued while DPoP was enabled.

## [0.5.0] - 2026-11-14

### Added

- `ServerConfig.SetClientStore` / `ClientStore`: an optional injection seam for the client store, so clients can live in a database instead of the static `SetClients` list. The container always wraps the injected store in `storage/impl.ValidatingClientStore`. The seam excludes `SetClients` and `SetClientsProvider`: setting both panics in `Freeze()` naming the client store and `SetClients`. The injected value must also implement the new `storage.ClientOriginLookup` (`FindClientsByAllowedOrigin(ctx, origin)`, an exact match on `AllowedCorsOrigins` without filtering on `Enabled`), which CORS decisions now read; `Freeze()` panics when it does not. With an injected store an origin is allowed only through an enabled client that passes configuration validation, and a lookup failure denies the origin; the CORS result for the static client list is unchanged. `storage/memory.MemoryClientStore` implements `ClientOriginLookup`.
- `storage.ClientRegistrationStore`: a writable client port for client registration, embedding `storage.ClientStore` so registrations and client reads share one value. `RegisterClient` is insert-only and returns revision 1; a registered or removed client id fails with `storage.ErrDuplicateHandle`, because removal leaves a tombstone. `UpdateClientRegistration` and `RemoveClientRegistration` carry the expected revision and fail with `storage.ErrVersionConflict` on a mismatch, leaving the record unchanged; a successful update returns the expected revision plus one. The store assigns revisions and ignores the `Revision` passed in. Missing records report `storage.ErrNotFound`. The port has no lookup by registration access token digest, no unfiltered enumeration and no `RemoveExpired`. The record type is `storage/models.ClientRegistration` (`Client`, `Revision`, `RegistrationAccessTokenDigest`, `RegistrationTime`).
- `storage.EncodeClient` / `storage.DecodeClient`: a versioned codec that turns a `*models.Client`, allowed grant types included, into opaque bytes for client registration adapters and back. An unknown version or malformed input is an error.
- `storage/memory.MemoryClientRegistrationStore` (`NewMemoryClientRegistrationStore()`): the in-memory client registration store, which also implements `storage.ClientOriginLookup`.
- `storagetest.RunClientRegistrationStoreSuite`: the conformance suite for client registration stores, covering tombstones, revision conflicts and retries, concurrent registration and update succeeding exactly once, and the exact origin lookup. It ships with `SuiteVersion` `2.0.0` (see the suite version entry under Changed).
- `ServerConfig.SetClientRegistrationStore`: the injection seam for the client registration store. The injected value also serves the client store seam (wrapped in `ValidatingClientStore`) and CORS decisions, must implement `storage.ClientOriginLookup`, and excludes `SetClientStore`, `SetClients` and `SetClientsProvider`; `Freeze()` panics otherwise. The seam is feature-required: once a feature that depends on it is enabled, `Freeze()` panics when it is not injected, and `AllowInMemoryFallback()` does not cover it. No such feature exists in this version, so existing assemblies behave as before.
- `storage.ErrInvalidClientConfiguration`: the sentinel for a client record that exists but fails configuration validation, and `extensions.IsClientRejected(err)`, which reports `storage.ErrNotFound` or `storage.ErrInvalidClientConfiguration`.
- `WicketOptions.UseSeeOtherRedirects`, off by default. Once set, every browser redirect produced by the authorize endpoint (`/connect/authorize`, GET and POST: back to the client in the `query` and `fragment` response modes, to the error page, the login page, the consent page and a custom interaction target), by its callback, and by the end session endpoint (`/connect/endsession`, GET and POST, to the logout page) answers 303 See Other instead of 302 Found, whatever the request method; the Location is unchanged. A 302 lets a user agent replay a POST body, which may carry credentials or authorization parameters, to the redirect target; RFC 9700 §4.12 and FAPI 2.0 Security Profile §5.3.2.2 recommend 303. The `form_post` response mode (200 HTML), the JSON endpoints and the redirects of the `auth` package's authentication handlers are unaffected. With the option off, responses are unchanged.
- `storage.AuthorizationCodeStore.TakeAuthorizationCode(ctx, handle)`: atomically removes the code stored under `handle` and returns an independent copy; a miss returns `storage.ErrNotFound`, and of concurrent takes of one handle exactly one succeeds. The store does not judge expiry. The token endpoint now redeems authorization codes with it: the code is taken first and only then checked for client binding, expiry, `redirect_uri`, scopes and PKCE, so a code that fails any of these checks is consumed as well. A take failure other than `storage.ErrNotFound` surfaces as an error, as a lookup failure did before; the separate removal step, whose failure answered `invalid_grant`, is gone. Concurrent exchanges of one code, also across replicas sharing a store, issue tokens once and answer `invalid_grant` to the others.
- Removal by client and by session, each returning how many records were removed: `RemoveAuthorizationCodesByClient` / `RemoveAuthorizationCodesBySession`, `RemoveRefreshTokensByClient` / `RemoveRefreshTokensBySession`, `RemoveReferenceTokensByClient` / `RemoveReferenceTokensBySession` (session taken from `Token.SessionId()`, the `sid` claim) and `RemoveUserConsentsByClient`. Removing nothing returns `(0, nil)`; an empty argument matches no record. An adapter without transactions may complete partially but must then return an error. The in-memory stores implement them; no core path calls them yet.
- `storagetest`: new MUST cases `TakeExactlyOnceUnderConcurrency`, `TakeMissingReturnsSentinel`, `TakeReturnsExpiredRecord`, `RemoveByClientIsolated`, `RemoveBySessionIsolated`, `ScopedRemoveEmptyArgumentMatchesNothing`, `RemoveMissingHandleSucceeds` (all seven store families), `RemoveBySubjectAndClientZeroMatchSucceeds` and `NoBackgroundGoroutinesScopedRemoval`. They are part of `SuiteVersion` `2.0.0` (see the suite version entry under Changed).

- `storage.PushedAuthorizationRequestStore`: the store port for pushed authorization requests (RFC 9126). `StorePushedAuthorizationRequest` is insert-only and fails with `storage.ErrDuplicateHandle` on an existing key, leaving the record unchanged; `GetPushedAuthorizationRequest` reads without consuming; `TakePushedAuthorizationRequest` atomically removes and returns the request, and of concurrent takes of one key exactly one succeeds; misses report `storage.ErrNotFound`, and reads and takes do not judge expiry. `RemoveExpired(ctx, cutoff)` reclaims only requests whose `RetentionExpiration` precedes `cutoff`. The port offers no enumeration. The record type is `storage/models.PushedAuthorizationRequest` (`ClientId`, `CreationTime`, `EntryExpiration` ending the handle's validity as an entry point, `RetentionExpiration` adding the interaction round-trip grace, and the opaque `Payload`).
- `storage.PushedAuthorizationRequestKey(requestURI)`: the only way to derive a pushed authorization store key, the unpadded base64url SHA-256 of the full `request_uri` (always 43 characters); a value without `storage.PushedAuthorizationRequestURIPrefix` (`urn:ietf:params:oauth:request_uri:`) or with nothing after it returns the new `storage.ErrInvalidRequestURI`. Stores never see the `request_uri` itself. `storage.NewPushedAuthorizationRequestURI()` generates a handle from 32 bytes of `crypto/rand`. `storage.ProtectPushedAuthorizationParameters` / `storage.UnprotectPushedAuthorizationParameters` turn authorization parameters into a versioned, data-protected payload and back; a nil protector, an unknown version, an unprotected container, malformed bytes or a failing `Unprotect` are errors. `storage.PushedAuthorizationRequestPurpose` is the data protection purpose of that payload.
- `storage/memory.MemoryPushedAuthorizationRequestStore` (`NewMemoryPushedAuthorizationRequestStore()`) and `storagetest.RunPushedAuthorizationRequestStoreSuite`, the conformance suite for pushed authorization request stores, including `MUST/RemoveExpiredKeepsRecordsInRoundTrip`. It ships with `SuiteVersion` `2.0.0` (see the suite version entry under Changed).
- `ServerConfig.SetPushedAuthorizationRequestStore` / `SetPushedAuthorizationRequestStoreProvider` and `ServerConfig.SetPushedAuthorizationDataProtectionProvider`: the pushed authorization store seam and a data protection seam that applies to pushed authorization payloads only, through a protector created with `storage.PushedAuthorizationRequestPurpose`. `Freeze()` panics when the data protection seam holds the default `services/impl.DataProtectionProvider`, which only encodes, whether or not pushed authorization is enabled; the seam has no fallback. Both seams are feature-required while pushed authorization is enabled, and `AllowInMemoryFallback()` does not cover them. The container's `dp.DataProtectionProvider` binding, used by key management and message cookies, is unchanged. Pushed authorization is enabled with `ServerConfig.EnablePushedAuthorizationRequests` (next entry); assemblies that do not enable it behave as before.
- Pushed authorization requests (RFC 9126), off by default. `ServerConfig.EnablePushedAuthorizationRequests(pushedauth.Options)` is the only switch (it panics after `Freeze()` or for a negative duration; query `PushedAuthorizationRequestsEnabled()`, `PushedAuthorizationRequestsOptions()`); `EndpointsOptions` has no switch for it. Once enabled, the pushed authorization store and data protection seams become required, and:
  - `POST /connect/pushedauthorization` (and `/connect/mtls/pushedauthorization` while mutual TLS client authentication is enabled) authenticates the client like the revocation endpoint (client secret, `private_key_jwt`, mutual TLS), refuses a body `client_id` naming another client, drops `client_secret`, `client_assertion` and `client_assertion_type`, validates the parameters like an authorize request (a `request_uri` is refused) and answers 201 `{"request_uri","expires_in"}` with `Cache-Control: no-cache, no-store`; validation failures answer 400 `{"error","error_description"}` (`error_description` omitted when empty), infrastructure failures 500. While the feature is disabled both routes fall through.
  - The authorize endpoint resolves a `request_uri` carrying the `urn:ietf:params:oauth:request_uri:` prefix from the store and never fetches it; while the feature is disabled such a value answers `invalid_request_uri`. An unknown handle, one of another client, an expired one or an unreadable payload answers `invalid_request_uri` without consuming the record. The pushed parameters replace the presented ones for validation; the validated request carries them in the new `validators/models.PushedAuthorizationRequestValues` (`PushedRequestUri`, `PushedParameters`), while `Raw`, the login and consent return URLs and the authorization parameters message store carry only `client_id`, `request_uri` and the entry receipt `par_entry_receipt`.
  - Two time limits: the entry lifetime (`Options.RequestUriLifetime`, default 60 seconds, or the client's `RequestUriLifetime`) is judged when the handle first reaches the authorize endpoint, which then issues an entry receipt protected by the pushed authorization protector; the authorize callback and `OidcReturnUrlParser` accept the longer retention (`Options.InteractionGracePeriod`, default 10 minutes) only with a valid receipt for that handle, so going straight to the callback cannot outlive `expires_in`.
  - The record is taken once, atomically, when the authorize endpoint answers the client (a code or an error redirect); the client is reloaded first, and a code is issued only after the take succeeded. A lost race or a missing client answers `invalid_request` without a code; another take failure is a server error. Login, consent and custom interaction redirects read without consuming.
  - Pushing can be required for every client (`Options.RequireForAllClients`) or per client (`ClientPushedAuthorizationMetadata.RequirePushedAuthorizationRequests`); such a client's plain authorize requests answer `invalid_request`.
  - Discovery advertises `pushed_authorization_request_endpoint`, `require_pushed_authorization_requests` and, when `mtls_endpoint_aliases` is advertised and its route is served, the alias of the endpoint; while the feature is disabled the keys are never advertised.
  - The core never reclaims expired records; hosts call `PushedAuthorizationRequestStore.RemoveExpired`.
- Package `pushedauth`: `Options` (`RequestUriLifetime`, `InteractionGracePeriod`, `RequireForAllClients`, `Clock`) and `Service` (`Push`, `Resolve`, `Consume`, `Required`) with the sentinels `ErrRequestUriInvalid`, `ErrClientRejected` and `ErrRequestUriConsumed`.
- Client metadata `models.ClientPushedAuthorizationMetadata` embedded in `models.Client`: `RequirePushedAuthorizationRequests` (RFC 9126 §6) and `RequestUriLifetime` (seconds, 0 for the server default). Client configuration validation rejects a client requiring pushed authorization while the feature is disabled and a negative `RequestUriLifetime`, so `FindClientById` returns `storage.ErrInvalidClientConfiguration` for it. `validators/impl.PushedAuthorizationFeature` is the feature declaration side interface the rule reads.
- `validators.AuthorizeRequestPhase` (`AuthorizeRequestPhaseEntry`, `AuthorizeRequestPhaseInteractionReturn`, `AuthorizeRequestPhasePush`), `handlers.PushedAuthorizationRequestHandler`, `handlers.PushedAuthorizationConsumer` with `SetPushedAuthorizationConsumer` on the authorize and callback handlers, `DiscoveryHandler.ServePushedAuthorization`, `validators/impl.AuthorizeRequestPushedStage` with `AuthorizeRequestValidator.SetPushedAuthorization`, and the constants `ProtocolRoutePathsPushedAuthorization`, `ProtocolRoutePathsMtlsPushedAuthorization`, `EndpointNamesPushedAuthorizationRequest`, `DiscoveryPushedAuthorizationRequestEndpoint`, `DiscoveryRequirePushedAuthorizationRequests` and `AuthorizeRequestPushedEntryReceipt`.

### Changed

- **Breaking**: the conformance suites `storagetest`, `sessiontest` and `keymgmttest` step `SuiteVersion` from `1.1.0` to `2.0.0` together. This release changes existing interfaces (the four store ports `AuthorizationCodeStore`, `RefreshTokenStore`, `ReferenceTokenStore` and `UserConsentStore` gain methods; `validators.AuthorizeRequestValidator.Validate` gains a parameter) and adds MUST cases that tighten the contract of existing methods (a single-handle removal of a missing handle must return nil), which calls for a major step; `sessiontest` and `keymgmttest` have no case changes and move only because the three suites stay in lockstep, so a host still checks a single number. wicket itself does not check `ConformsTo()`; a host that compares an adapter's `ConformsTo()` with `SuiteVersion` for equality refuses an adapter whose credential still reads `1.1.0` until it passes the 2.0.0 suites and returns `2.0.0`. `replaytest.SuiteVersion` stays `1.0.0`: it is versioned on its own and compared separately. Adapters maintained outside this repository need the same update; see Adapter migration below.
- **Breaking**: `storage/impl.ValidatingClientStore.FindClientById` returns `storage.ErrNotFound` when the inner store returns `(nil, nil)`, and an error wrapping `storage.ErrInvalidClientConfiguration` (with the client id and the validation message) when validation fails, instead of `(nil, nil)` and an unclassified error.
- Client existence gate: every credential redemption and introspection path now tells a rejected client from a client store failure. Client authentication at the token, revocation, backchannel authentication and device authorization endpoints (shared secret, `private_key_jwt` and mutual TLS) answers `invalid_client` for a missing, disabled or invalid client as before, and 500 with the fixed body `Internal Server Error` for any other client store error, which previously answered `invalid_client`. Access token validation (introspection, userinfo) and identity token validation (`id_token_hint` at end session) keep their invalid-token results for a rejected client and return the store error, answered as a server error, for any other failure. Authorization codes, refresh tokens and tokens of a deleted client therefore stop working at the next redemption or introspection; a resource server that validates JWT access tokens offline accepts them until they expire.
- **Breaking**: `services/memory.NewMemoryCorsPolicyService` takes a `storage.ClientOriginLookup` and an optional acceptance function instead of a client slice.
- Store seam validation: each store seam now carries a category. The authorization parameters message store and the client store are optional: `Freeze()` no longer fails when the authorization parameters message store is not injected and no fallback is declared, and it logs one warning per optional seam left uninjected when a logger is set. The other ten seams stay required.
- **Breaking**: `storage.AuthorizationCodeStore`, `storage.RefreshTokenStore`, `storage.ReferenceTokenStore` and `storage.UserConsentStore` gain the methods listed under Added; adapters must implement them.
- **Breaking**: `validators.AuthorizeRequestValidator.Validate` takes a trailing `phase validators.AuthorizeRequestPhase`. Callers declare the phase: the authorize endpoint passes `AuthorizeRequestPhaseEntry` (the zero value), the authorize callback and `OidcReturnUrlParser.Parse` pass `AuthorizeRequestPhaseInteractionReturn`, the pushed authorization endpoint passes `AuthorizeRequestPhasePush`. Requests without a pushed `request_uri` validate as before in every phase except `Push`, which refuses a `request_uri`. Custom implementations of the interface must add the parameter.
- The identity token issued by the authorize endpoint takes its `nonce` from the validated request instead of the raw parameters; the value is the same for every request that does not use pushed authorization.
- **Breaking**: every single-handle removal (`RemoveAuthorizationCode`, `RemoveRefreshToken`, `RemoveReferenceToken`, `RemoveUserConsent`, `PersistedGrantStore.Remove`, `DeviceFlowStore.RemoveByDeviceCode`, `RemoveBackchannelAuthenticationRequest`) must return nil for a handle that does not exist, and `RemoveReferenceTokens` must return nil when nothing matches. With this contract a revocation that loses a race with a concurrent revocation of the same token answers 200 instead of a server error. Adapters that report a missing handle as an error must change.

### Adapter migration

The ports changed in this release, item by item, and what an adapter or a host has to do:

- Pushed authorization request port: implement `storage.PushedAuthorizationRequestStore` (insert-only store, non-consuming read, atomic take, `RemoveExpired` by `RetentionExpiration`) if the adapter serves pushed authorization, keyed only by `storage.PushedAuthorizationRequestKey`; store `ClientId` and the three time fields as visible columns and the payload as opaque bytes; pass `storagetest.RunPushedAuthorizationRequestStoreSuite`. Hosts that enable pushed authorization inject it with `SetPushedAuthorizationRequestStore`.
- Writable client port: implement `storage.ClientRegistrationStore` together with `storage.ClientOriginLookup` if the adapter serves client registration; store the client through `storage.EncodeClient` / `storage.DecodeClient` as opaque bytes with the client id, revision, registration access token digest and registration time as visible fields; keep tombstones for removed client ids; pass `storagetest.RunClientRegistrationStoreSuite`. No feature in this release requires the seam.
- Atomic authorization code redemption: implement `AuthorizationCodeStore.TakeAuthorizationCode` as one atomic find-and-delete (for example `DELETE ... RETURNING`), returning `storage.ErrNotFound` on a miss and not judging expiry; `RemoveAuthorizationCode` keeps its semantics.
- Optional `ClientStore` seam: host side. A client store adapter injected with `SetClientStore` must also implement `storage.ClientOriginLookup` and return `storage.ErrNotFound`, never `(nil, nil)`, for a missing client. Adapters of the other ports need no change.
- Seam categories: host side, no adapter change. The authorization parameters message store and the client store seams are optional; the client registration and pushed authorization seams are feature-required and not covered by `AllowInMemoryFallback()`.
- Pushed authorization data protection seam: host side, no adapter change. Hosts enabling pushed authorization inject a real protection provider with `SetPushedAuthorizationDataProtectionProvider`; the default encoding-only provider is refused and there is no fallback.
- `AuthorizeRequestValidator` phase input: no store adapter change. Custom validator implementations and direct callers add the trailing `validators.AuthorizeRequestPhase` parameter.
- `ValidatingClientStore` sentinels and `storage.ErrInvalidClientConfiguration`: host side. Code that inspected the validator's results checks `storage.ErrNotFound` / `storage.ErrInvalidClientConfiguration` (or `extensions.IsClientRejected`) instead of `(nil, nil)`; a client store adapter returns infrastructure failures as they are, not wrapped as `storage.ErrNotFound`.
- Removal by client and by session: implement `RemoveAuthorizationCodesByClient` / `BySession`, `RemoveRefreshTokensByClient` / `BySession`, `RemoveReferenceTokensByClient` / `BySession` and `RemoveUserConsentsByClient`, returning the count, `(0, nil)` for no match and for an empty argument; store `client_id` and the session identifier (for reference tokens `Token.SessionId()`) as visible, indexed columns. `PersistedGrantStore` keeps using `RemoveAll` with its filters.
- CORS policy service: host side. Hosts that build `services/memory.NewMemoryCorsPolicyService` directly pass a `storage.ClientOriginLookup` (and an optional acceptance function) instead of a client slice.
- Client existence gate: host side, no adapter change beyond returning `storage.ErrNotFound` for a missing client. Credential redemption and introspection now answer a server error, not an invalid credential, for any other client store error.
- Read-time secret rotation for RFC 7592: this release delivers only the update semantics it depends on (`UpdateClientRegistration` with an expected `Revision`, failing with `storage.ErrVersionConflict`); the rotation itself comes with the RFC 7592 management endpoint in a later release.
- Single-handle removal of a missing handle (`RemoveAuthorizationCode`, `RemoveRefreshToken`, `RemoveReferenceToken`, `RemoveUserConsent`, `PersistedGrantStore.Remove`, `DeviceFlowStore.RemoveByDeviceCode`, `RemoveBackchannelAuthenticationRequest`) and `RemoveReferenceTokens` with no match must return nil.
- Return `2.0.0` from `ConformsTo()` on every `storage`, `session` and `keymgmt` store type once it passes the 2.0.0 suites; a replay registry keeps returning `replaytest.SuiteVersion` (`1.0.0`).

## [0.4.0] - 2026-11-13

### Added

- Mutual TLS client authentication (RFC 8705), off by default. `ServerConfig.EnableClientCertificateAuthentication(clientcert.Options)` enables `tls_client_auth` (certificate chained to `Options.TrustedAuthorities`, which also must carry the client authentication extended key usage when it has one, and matched against exactly one registered `TlsClientAuthSubjectDn` / `TlsClientAuthSanDns` / `TlsClientAuthSanUri` / `TlsClientAuthSanIp` / `TlsClientAuthSanEmail`) and `self_signed_tls_client_auth` (certificate equal to the first `x5c` member of a key in the inline `Jwks`) at the token, revocation, backchannel authentication and device authorization endpoints; the request must carry `client_id`. The client certificate is read from the TLS connection unless the host injects a `clientcert.CertificateSource` through `ServerConfig.SetClientCertificateSource`; no proxy header is trusted. The `/connect/mtls/*` alias routes are served by the main handlers once enabled and fall through otherwise. Discovery advertises the tls methods and `mtls_endpoint_aliases` only when the feature is enabled and `MutualTls.Enabled` is on; `tls_client_certificate_bound_access_tokens` is advertised as described in the certificate bound access token entry below. Client registrations requiring a tls method that is not enabled are rejected by configuration validation. All failures answer `invalid_client` without a description. Fixed the path and sub-domain forms of `mtls_endpoint_aliases`, which lacked the slash before the route. See `docs/mtls-client-auth-guide.md`.
- Certificate bound access tokens (RFC 8705 §3), available while mutual TLS client authentication is enabled. A client registering the new `TlsClientCertificateBoundAccessTokens` flag receives, at the token endpoint and its `/connect/mtls/token` alias, access tokens bound to the client certificate presented with the token request: the JWT carries `cnf` with `x5t#S256`, the unpadded base64url SHA-256 thumbprint of the certificate's DER encoding, and a reference access token record keeps the same value as `Token.Confirmation` and as a `cnf` claim. The client may authenticate with its certificate or in any other way; a token request without a client certificate answers `invalid_client` without a description before any authorization code, refresh token or device code is redeemed. A refresh binds the new access token to the certificate presented with the refresh request, whether or not `UpdateAccessTokenClaimsOnRefresh` is set; the refresh token itself is not bound. The userinfo endpoint answers 401 `invalid_token` when a token carrying `cnf.x5t#S256` is presented without that certificate or its confirmation is malformed; tokens without it behave as before. Introspection returns `cnf` for bound JWT and reference tokens. The `auth/jwt` bearer handler gains `Options.CertificateBindingSource`: when set, a bound token presented without its certificate fails authentication with `jwt.ErrCertificateBindingMismatch`; nil keeps the previous behavior. Discovery advertises `tls_client_certificate_bound_access_tokens: true` while the feature is enabled and `MutualTls.Enabled` is on. Configuration validation rejects the flag while mutual TLS client authentication is not enabled, for a public client (`RequireClientSecret=false`) and together with `AllowAccessTokensViaBrowser`. New package `certbind` holds the thumbprint and check algorithm. `services/impl.NewTokenService` takes a trailing `services.AccessTokenConfirmation` (nil leaves tokens unbound); code that builds it through the composition root needs no change. See `docs/mtls-client-auth-guide.md`.
- Package `replay`: the port for one-time identifiers, so that the `jti` of a client assertion or of a DPoP proof is accepted once within its validity window, also across replicas. `replay.Registry` has two operations and no read, removal by key or enumeration. `Register(ctx, key, expiresAt)` is an atomic insert: it returns nil for a key that is not registered and `replay.ErrDuplicateHandle` for one that is and has not been reclaimed, leaving the stored record and its expiry instant unchanged; concurrent registrations of one key succeed exactly once. `RemoveExpired(ctx, cutoff)` drops the records expiring strictly before `cutoff` and returns how many; it is the only way records leave a registry, and the host drives it. A registry never reads a clock: a key past its expiry instant stays a duplicate until it is reclaimed. `replay.ErrDuplicateHandle` is a value of this package, distinct from `storage.ErrDuplicateHandle`; the package also defines `replay.ErrInvalidArgument` (empty key or zero expiry instant) and `replay.ErrInvalidKeyInput`. `replay.Key(purpose, qualifier, jti)` is the only source of registry keys: a `replay.Purpose` from `replay.PurposeClientAssertion()` or `replay.PurposeDPoPProof()`, the qualifier and the `jti` are encoded with length prefixes and hashed with SHA-256 into 64 lowercase hexadecimal characters. `replay.MemoryRegistry` (`replay.NewMemoryRegistry()`) keeps the records in process memory and is correct within one process only. No authentication path uses the registry yet.
- Package `replay/replaytest`: the conformance suite for `replay.Registry`, run with `RunRegistrySuite(t, newRegistry, opts...)`; `WithMay(true)` adds the MAY cases, and `KeyVectors()` returns test vectors for `replay.Key`. Its `SuiteVersion` is `1.0.0` and is versioned on its own: it is not part of the lockstep of `storagetest`, `sessiontest` and `keymgmttest`, whose versions do not change. A replay registry adapter is a store type of its own and hosts compare its `ConformsTo()` with `replaytest.SuiteVersion` separately. Passing the suite does not prove that an adapter registers atomically or that it avoids native expiry of its medium; see the package documentation.
- `ServerConfig.SetReplayRegistry`, `SetReplayRegistryProvider`, `ReplayRegistry` and `AllowInMemoryReplayRegistryFallback`: the injection seam for the replay registry. The seam is required only once a feature that depends on it is enabled, and no such feature exists in this version, so existing assemblies behave as before and the provider is never called. Once required, `Freeze()` panics when no registry was injected; `AllowInMemoryFallback()` does not cover this seam, and only `AllowInMemoryReplayRegistryFallback()` accepts the in-memory registry for it, with a warning logged when it is used.
- `private_key_jwt` client authentication (RFC 7523), off by default and enabled with `ServerConfig.EnablePrivateKeyJwt(clientassertion.Options)` before `Freeze()`. Once enabled, the token, revocation, backchannel authentication, device authorization and introspection endpoints accept a `client_assertion` of type `urn:ietf:params:oauth:client-assertion-type:jwt-bearer` from a client whose `TokenEndpointAuthMethod` is `private_key_jwt` and that registered its public keys as an inline `Jwks` or a `JwksUri` (the introspection endpoint from an API resource holding a `JWK` typed secret). The assertion must be signed with an asymmetric algorithm (`RS*`, `PS*`, `ES*`; `none` and `HS*` are refused), carry `iss` = `sub` = the client id, an unexpired `exp` within the lifetime bound and a `jti`, and its `aud` must be the issuer identifier of the server as its only value (RFC 10070): the token endpoint URL is not accepted. Each `jti` is accepted once through the replay registry, which becomes a required seam. Every failed assertion answers the endpoint's `invalid_client` response without a description; a replay registry failure answers 500 with the fixed body `Internal Server Error`. Discovery lists `private_key_jwt` and `token_endpoint_auth_signing_alg_values_supported` only while the feature is enabled. A client registered for `private_key_jwt` does not load in an assembly that has not enabled the feature. See `docs/private-key-jwt-guide.md`.
- Request objects can be restricted to asymmetric signatures, off by default. `ServerConfig.RequireAsymmetricRequestObjects()` (query `AsymmetricRequestObjectsRequired()`) accepts a request object, by value or by `request_uri`, only when it is a compact JWS whose header names `RS256/384/512`, `PS256/384/512` or `ES256/384/512`; it is verified with the client's non-symmetric keys only, so an HMAC signature is refused whatever the header declares. Every refusal answers `invalid_request_object`. Discovery then advertises only those nine values under `request_object_signing_alg_values_supported`, a host value included, and drops the key when nothing remains. The default assembly keeps accepting `HS*` request objects. Once the option is on, a client that registered only symmetric keys can no longer use request objects. The `request` parameter of the backchannel authentication endpoint is not verified as a signed request object and is not affected by the option.
- Per-client signing algorithms for `private_key_jwt`: the new client metadata `ClientAuthenticationMetadata.TokenEndpointAuthSigningAlgorithms` narrows the algorithms a client's assertions may use. An assertion whose `alg` is not listed answers `invalid_client` before any key is read or `jti` registered. A non-empty list on a client that does not use `private_key_jwt`, or with a value outside the server's `private_key_jwt` algorithms, fails client configuration validation. An empty list keeps the previous behavior. See `docs/private-key-jwt-guide.md`.
- The `client_credentials` grant can be restricted to authenticated clients, off by default. With `ServerConfig.RequireClientCredentialsAuthentication()` (query `ClientCredentialsAuthenticationRequired()`) the token endpoint answers 400 `invalid_client` to a `client_credentials` request, the grant type taken from the body or the query string, unless the client authenticated with a required secret, a `private_key_jwt` assertion or a tls client certificate (RFC 6749 §4.4). Other grants and other endpoints are unaffected.

## [0.3.0] - 2026-11-13

### Added

- Token revocation endpoint (RFC 7009) at `POST /connect/revocation`, handled by `handlers.TokenRevocationHandler` and registered through the composition root. With `EnableTokenRevocationEndpoint` off it answers 404 and is not advertised. Clients authenticate as at the token endpoint. A failed client authentication answers `invalid_client`: 401 with a `WWW-Authenticate` challenge (`Basic realm="wicket"` for Basic) when the request carries an `Authorization` header, 400 otherwise. A missing token answers 400 `invalid_request`, as does an empty body when the credentials are in the `Authorization` header (with no such header an empty body carries no credentials and answers 400 `invalid_client`); a `token_type_hint` other than `access_token` / `refresh_token` answers 400 `unsupported_token_type`. Unknown tokens, already revoked tokens and tokens of another client, when not JWT shaped, answer 200 with an empty body and no-cache headers; another client's token is left untouched. Revoking a refresh token also revokes the reference access tokens of the same subject and client. Reference access tokens are those issued to clients configured with `AccessTokenType=Reference` (see the entry under Changed) and those a host stores itself; clients on the default form receive JWT access tokens, which cannot be revoked. Submitting a JWT shaped token (one containing a `.`) answers 400 `unsupported_token_type` and revokes nothing; the token stays valid until it expires. The JWT form is decided by the same rule access token validation uses, whatever the hint and without verifying the signature. Known limitations: a `token_type_hint` naming the wrong token type does not extend the search to the other type, as RFC 7009 §2.1 requires, so such a token is not revoked; a handle containing a `.` that a host stores itself, refresh or reference, answers 400 `unsupported_token_type` and cannot be revoked through this endpoint; with `EnableTokenRevocationEndpoint` off, a custom discovery entry named `revocation_endpoint` that a host points back at this server's revocation route still appears in the discovery document, although the endpoint answers 404. Parameters are read from the request body only.
- `results.ClientAuthenticationErrorResult` writes the `invalid_client` answer with its headers set before the status code.
- Discovery: `revocation_endpoint` is advertised again in the default assembly now that the route is registered.
- Device authorization endpoint (RFC 8628) at `POST /connect/deviceauthorization`, handled by `handlers.DeviceAuthorizationHandler` and registered through the composition root. With `EnableDeviceAuthorizationEndpoint` off it answers 404 and is not advertised. Clients authenticate as at the token endpoint; a public client sends only `client_id`. A failed client authentication answers `invalid_client` (401 with a `WWW-Authenticate` challenge when the request carries an `Authorization` header, 400 otherwise); `invalid_request`, `invalid_scope` and `unauthorized_client` answer 400 with a JSON body holding only the error code and no-cache headers, written by the new `results.DeviceAuthorizationErrorResult`. Parameters are read from the request body only. The device then polls the token endpoint with the `device_code` grant type and receives `authorization_pending`, `slow_down`, `access_denied`, `expired_token` or tokens; a device code is redeemed once. Known limitations: user codes come from `math/rand` and wicket does not rate-limit user code attempts, which is left to the host's verification page; `verification_uri_complete` does not URL-encode the user code; lookup and removal of a device code are not atomic, so concurrent polls may redeem it twice.
- `services.DeviceFlowInteractionService` for the host's verification page: `GetAuthorizationContext` returns the client, requested scopes, whether the request is OpenID Connect and the expiry for a user code; `Approve` authorizes the device for an authenticated subject (which must carry `sub`) and a subset of the requested scopes; `Deny` rejects it. Errors are reported in a fixed order through `ErrDeviceFlowUserCodeNotFound`, `ErrDeviceFlowUserCodeExpired`, `ErrDeviceFlowUserCodeAlreadyHandled` and, for `Approve`, `ErrDeviceFlowInvalidApproval`. Approval narrows the requested scopes to the approved ones, so a refresh token cannot widen the grant. No consent is remembered. Resolve it from the request scope like `services.InteractionService`.
- `storagetest`: MUST case `UpdateVisibleByDeviceCode` for `DeviceFlowStore`: after `UpdateByUserCode`, both `FindByUserCode` and `FindByDeviceCode` return the new record, including its authorization state, scopes, subject and session id.
- Discovery: `device_authorization_endpoint` and the `device_code` grant type are advertised again in the default assembly now that the route is registered.
- OpenID Connect Back-Channel Logout 1.0 delivery. When server-side sessions and the check-session endpoint are both enabled, loading the end-session callback iframe signs a logout token for every client of the ended session that registered a `BackChannelLogoutUri` and posts it as `application/x-www-form-urlencoded`. The token is typed `logout+jwt`, lives two minutes and carries `iss`, `aud`, `iat`, `nbf`, `exp`, a fresh `jti`, the back-channel logout `events` object, `sid` and the session's `sub`, never `nonce`; it follows the client's identity token signing algorithms. Before anything is sent the logout context is checked against the session store (the session must exist and be current, the subject must match, and only clients recorded for the session are notified). Posts run concurrently and the callback waits for them for at most five seconds; failing relying parties are only logged. A callback loaded more than 300 seconds after its logout context was written does not deliver again. Known limitations: delivery depends on the browser loading the callback iframe; reloading it within 300 seconds delivers again; sign-outs that bypass `/connect/endsession`, and session expiry or deletion, send nothing; logout context handles are not integrity protected by the default data protection, so a party knowing a session's `sid` can make that session's relying parties receive a logout notification; logout URIs are not filtered for internal addresses.
- Discovery: `backchannel_logout_supported` and `backchannel_logout_session_supported` are advertised when server-side sessions and the check-session endpoint are both enabled. The default assembly keeps server-side sessions off and does not advertise them.
- Identity tokens issued within a user session carry the session id as `sid`.
- Hosts that inject a back-channel logout HTTP client through `ServerConfig.SetBackChannelLogoutHttpClient` must give it a timeout: response bodies are not closed, so connections are reclaimed only by the timeout.
- `handlers.NewAuthorizeHandlerWithOptions`, `handlers.NewAuthorizeCallbackHandlerWithOptions`, `handlers.NewTokenHandlerWithOptions`, `handlers.NewIntrospectionHandlerWithOptions` and `handlers.NewBackchannelAuthenticationHandlerWithOptions` take the same arguments as the existing constructors plus `*config_options.WicketOptions` (before the logger; last for the backchannel authentication handler), so a handler a host builds itself enforces its endpoint switch. Nil options leave the endpoint on. The existing constructors keep their signatures and behavior.

### Changed

- **Breaking**: `services/impl.NewBackchannelLogoutService` takes the token creation service, client store, issuer name service, session store, system clock and options, and `handlers.NewEndSessionCallbackHandler` takes the back-channel logout service, the logout context message store and the system clock. Code that builds them through the composition root needs no change.
- Signing out of the default sign-out scheme through the authentication service also clears the server-side session cookie; signing out of any other scheme leaves it.
- **Breaking**: the conformance suites `storagetest`, `sessiontest` and `keymgmttest` step `SuiteVersion` from `1.0.0` to `1.1.0` together, because `storagetest` gains the MUST case `UpdateVisibleByDeviceCode`. Hosts compare an adapter's `ConformsTo()` with `SuiteVersion` for equality, so an adapter whose credential still reads `1.0.0` is refused at assembly until it passes the 1.1.0 suites and returns `1.1.0`. Adapters maintained outside this repository need the same update.
- **Breaking**: `TokenRevocationResponse.Success` now means the token was found (false for a miss, with no error); the endpoint answers 200 either way.
- **Breaking**: `EnableAuthorizeEndpoint`, `EnableTokenEndpoint`, `EnableIntrospectionEndpoint` and `EnableBackchannelAuthenticationEndpoint` now switch off the endpoint itself. With a switch set to false, the authorize and authorize callback routes, the token route, the introspection route or the backchannel authentication route answers 404 with an empty body to every request, whatever its method, content type or credentials, and before anything of the request is read; until now these switches only removed the discovery advertisement and the routes kept serving. The defaults are unchanged (all `true`), so only hosts that explicitly set one of these switches to false are affected. A switch closes only its own endpoint: with the token endpoint off, for example, the authorize, device authorization and backchannel authentication endpoints still start flows whose codes can no longer be redeemed. The switch is enforced by handlers built through the composition root; a handler built directly with one of the existing constructors holds no options and keeps serving whatever the switch says. Known limitation: with a switch off, a custom discovery entry named `authorization_endpoint`, `token_endpoint`, `introspection_endpoint` or `backchannel_authentication_endpoint` that a host points back at this server's route still appears in the discovery document, although the endpoint answers 404.
- **Breaking**: a client configured with `AccessTokenType=Reference` now receives an opaque handle as its access token, and the token itself is written to the `ReferenceTokenStore`; until now this setting was silently ignored and such a client received a JWT. The handle is 64 upper-case hexadecimal characters and never contains a `.`. It is issued for every grant at the token endpoint and also by the authorize endpoint for response types that include `token`; identity tokens stay JWTs, and `token_type`, `expires_in`, `scope` and `refresh_token` in the token response are unchanged. Introspection answers `active=true` for an issued handle, userinfo accepts it, the owning client can revoke it at the revocation endpoint with immediate effect, and revoking a refresh token ends every handle of the same subject and client, including those of the user's other sign-ins to that client. Clients on the default `AccessTokenType=Jwt` are unaffected. What hosts with such clients need to know:
  - Resource servers that validated these clients' access tokens locally as JWTs must switch to introspection. The `auth/jwt` bearer scheme does not accept handles.
  - The `ReferenceTokenStore` now receives one record per issued access token, including one per refresh token exchange; an exchange does not revoke the handle issued before it. Revoked records are removed, but expired ones stay until the host calls `RemoveExpired` on the store: wicket runs no background task, so a store that is never reclaimed grows without bound. A host that injects no store fails at `Freeze()` unless it called `AllowInMemoryFallback()`; with the fallback, or without `Freeze()`, records live in process memory, so handles are lost on restart and are not shared between replicas.
  - Refresh tokens issued before this change, or before a client was switched to `Reference`, keep redeeming JWT access tokens along their whole refresh chain, for as long as that chain lives: by default an exchange reuses the access token model saved with the refresh token, which carries the form it was issued with. Those JWTs cannot be revoked, and nothing in the token response points this out. To move such sessions over, revoke or expire the earlier refresh tokens so users sign in again, or set `UpdateAccessTokenClaimsOnRefresh` on the client so every exchange assembles the access token from the current client configuration; neither reaches JWTs already issued. The same holds in the other direction for a client switched back to `Jwt`, and handles already stored stay valid until they expire or are revoked.
  - A host-provided `RefreshTokenStore` must round-trip the access token model saved inside a refresh token, at least its `ClientId` and `AccessTokenType`; a store that drops `AccessTokenType` makes exchanges issue JWTs. The conformance suite does not check this yet.
  - When the store refuses the write, no token of either form is issued: the token endpoint answers with the same non-200 status as other infrastructure errors and a fixed text. The store's own error text is not passed on to the response or to wicket's log, because a store may echo the handle it was given; the error chain still reaches the store's error through `errors.Is` / `errors.As`, and wicket logs the client id, a category and the error's type. The detailed cause has to be logged by the store itself, without the handle or the record content. Records stored for a request that fails at a later step are not rolled back; their handles were never handed out and they stay until they expire and are reclaimed.
  - Handles are generated inside the token service the same way refresh token handles are by default; the generator cannot be replaced by the host.

### Fixed

- Server-side sessions: a session created at sign-in was never restored on later requests, because nothing loaded it from the session cookie. Identity tokens carried no `sid`, end-session found no session or participating clients, and no front-channel or back-channel logout happened. `UserSession` now restores the session once per request when its session id, client list or client registration is first needed, and adopts it only when the request's authenticated user is the session's subject; otherwise the session cookie is cleared. With server-side sessions enabled, access and identity tokens therefore carry `sid` and the end-session callback renders the front-channel iframes.
- Back-channel logout: without a host-provided HTTP client the back-channel logout client was nil, so the first delivery would panic. A default client with a five second timeout that does not follow redirects is used instead.
- Token revocation: a refresh token submitted without `token_type_hint` was not revoked, because a miss in the reference token store was reported as success and the refresh token store was never consulted. A miss in either store is reported as not found again, so the no-hint path reaches the refresh token store.
- Token revocation: the request validator logged its whole validation result at debug level, so a revocation request that carried a token wrote that token to the log. Under a JSON log handler, which the default logger uses at debug level, the record also held the client object, including the client's hashed secrets. The record now carries only the client id, the token type hint and the error code. The revocation endpoint is new in this release, so earlier releases wrote this record only where a host called the validator itself; tokens and hashed secrets already written to a debug log should be treated as exposed.
- Device flow: polling throttling never took effect, because the last poll time was written with `time.Time.String()` and read back as RFC 3339; it is now written and read as RFC 3339 with fractional seconds, so a second poll within the interval answers `slow_down`. A client without `PollingInterval` now falls back to `DeviceFlow.Interval` instead of dereferencing a nil pointer.
- Device flow options: `DeviceFlow` was left at its zero value in the default options, so the advertised `interval` was 0 and a client without `PollingInterval` was never throttled. The defaults are now applied: `Interval` is 5 seconds (RFC 8628 §3.2) and `DefaultUserCodeType` is numeric.
- Device authorization: the success response was sent as `text/plain` because the status line was written before `Content-Type`; it is now `application/json`. An empty `verification_uri_complete` is left out instead of written as an empty string.
- Device code grant: the validated scopes were never handed on, so tokens issued for a device code carried no scope or audience and no refresh token was issued. They now carry the authorized scopes, and approving `offline_access` issues a refresh token.
- In-memory device flow store: `UpdateByUserCode` replaced the record under the user code only, so polling by device code never saw the user's decision. Both lookups now return the updated record, and updating an unknown user code fails with `storage.ErrNotFound`.

## [0.2.1] - 2026-11-12

### Changed

- **Breaking**: `handlers.NewDiscoveryHandler` takes three new parameters, `endpointPaths []string`, `backChannelLogout services.BackchannelLogoutService` and `secretParsers validators.SecretsListParser`, which carry the assembly facts the discovery filter needs. Code that builds the handler through the composition root needs no change; code calling the constructor directly must pass them (a nil `endpointPaths` means no route is registered, so every endpoint URL under the base URL is withdrawn).

### Fixed

- Discovery: the configuration document now advertises only what the running assembly can serve. Endpoint URLs under the server's base URL are kept only when a route is registered for them, so `revocation_endpoint` and `device_authorization_endpoint` (no handlers yet, previously answering 404) are no longer advertised, and `device_code` is dropped from `grant_types_supported` together with the device authorization endpoint. `backchannel_logout_supported` / `backchannel_logout_session_supported` are advertised only when the back-channel logout service reports that it delivers notifications (the default service does not). `authorization_response_iss_parameter_supported` follows `EmitIssuerIdentificationResponseParameter`. Mutual TLS entries need registered tls client authentication parsers: each of `tls_client_auth` / `self_signed_tls_client_auth` is advertised only when a parser provides that method; without any such parser `tls_client_certificate_bound_access_tokens` and `mtls_endpoint_aliases` are withheld, and otherwise each alias is kept only when its primary endpoint is still advertised and, for a path-form alias (no `MutualTls.DomainName`), its path is a registered route. When `MutualTls.Enabled` is on and any mutual TLS entry is removed, a warning is logged. Host `CustomEntries` are not filtered, except under a key the generator itself writes: such a key is always filtered, including when the generator's switch for it is off and the custom value is the one in the document, so a custom entry cannot re-advertise a withdrawn capability. Lists under those keys are judged element by element whether they hold `[]string` or `[]any`, and an endpoint value that is not an absolute URL is withdrawn. Keys the generator never writes, such as `registration_endpoint`, stay with the host. Once a missing capability is implemented and registered, its advertisement returns without further changes.
- Tests: an assembly-level guard checks the default and the all-switches-on assemblies: every advertised endpoint must route to a handler (not 404), every capability advertised as `true` must map to implementation evidence, the advertised grant types and authentication methods must agree with the assembly, and every registered route other than the discovery document and the interaction callbacks must be advertised.
- Docs: README and API contracts describe device authorization, token revocation and back-channel logout delivery as not yet available, and document the discovery filtering rules.
